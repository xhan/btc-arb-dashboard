# 交易对暂停功能设计

## 背景

当前主看板会把配置中的交易对持续加入报价轮询队列。交易对数量增加后，队列 lap time 变长，API 轮询速度下降，进而影响主看板报价刷新速度。

本次需求需要给单个交易对增加“暂停”能力。暂停后的语义等同“伪删除”：

- 不再参与报价轮询
- 不再参与套利路径计算
- 不再参与路径报警与规则报警
- 不再出现在新增路径报警腿候选中

同时，用户不希望暂停后的交易对从主看板消失，而是继续显示在原位置，便于识别和随时恢复。

## 目标

- 让单个交易对可以被快速暂停和恢复，无确认弹窗
- 暂停后立刻减少报价队列中的任务数，改善 API 轮询速度
- 暂停后的交易对在主看板继续显示，但以明显灰态与正常交易对区分
- 在不增加额外 metadata 请求成本的前提下，若交易对此前已经成功报过价，则暂停后保留已有代币名称展示

## 非目标

- 不新增“暂停交易对分组”或独立管理页
- 不把 symbol 持久化回配置
- 不改造底层套利算法或报警算法的数据结构
- 不为暂停/恢复增加确认弹窗

## 用户可见行为

### 主看板交互

- 每条交易对右侧操作区，在“设置”按钮左边增加一个暂停/恢复按钮
- 正常状态显示暂停图标，点击后立即暂停
- 暂停状态显示恢复图标，点击后立即恢复
- 暂停和恢复都不弹确认框

### 暂停后的展示

- 交易对仍保留在主看板原位置
- 整行增加灰态样式，和正常报价状态明显区分
- 结果区统一显示“已暂停”
- 反向报价小字隐藏
- 错误态红框、报警高亮、未读报警痕迹一并清除
- 如果该交易对之前已经成功报过价，则继续保留 `quoteMonitorState` 中已有的 `fromSymbol/toSymbol` 展示
- 如果该交易对此前从未成功报过价，则维持现有兜底展示行为

### 恢复后的展示

- 交易对立即退出灰态
- 重新加入报价队列
- 立即触发一次主向报价
- 新报价成功后恢复正常主报价、反向报价、路径计算和报警参与

## 数据模型

每个交易对配置新增可选字段：

```json
{
  "paused": true
}
```

约束：

- `paused` 缺省时视为 `false`
- `paused === true` 表示该交易对处于停用状态
- 该字段与 `showInverse`、`preferredSource`、`alerts` 并列存在，不改变原有字段语义

## 设计原则

### 统一在上游过滤活跃交易对

不在 `arb-paths.js`、`arb-special-utils.js`、`path-alert-utils.js` 等算法模块里分散判断 `paused`，而是在消费这些算法之前，统一过滤出“活跃交易对”。

这样可以保证：

- 报价队列、套利路径、报警、候选列表共享同一套暂停语义
- 改动集中在 orchestrator 层，回归面更清晰
- 不会把暂停逻辑散落到多个算法实现中

### 暂停后清理运行态价格，但保留已解析 symbol

暂停操作会清理价格和报警相关运行态，防止旧数据继续参与计算；但不主动清掉已有 `fromSymbol/toSymbol`，从而满足“已报过价的交易对暂停后仍保留代币展示”的需求。

## 受影响模块与设计

### 1. 主看板队列与运行态

文件：

- `app.js`

新增概念：

- `isQuotePaused(quote)`：统一判断交易对是否暂停
- `getActiveQuotes(quotes)`：过滤掉暂停交易对
- `clearPausedQuoteRuntimeState(quoteId)`：清理暂停时需要移除的运行态价格/报警/错误信息，但保留 symbol

行为设计：

- `addToQueue(quote)` 遇到暂停交易对时不生成任务
- `processQueue(type)` 发现队列中的目标交易对已暂停时，直接从队列中移除，不再发请求
- 初始化加载配置后，只把未暂停交易对加入 scheduler
- 恢复交易对时重新入队，并立即 `fetchSingleQuote(quote, 'main')`

暂停时清理的运行态内容：

- `lastRawPrice`
- `lastResultText`
- `inverseRawPrice`
- `inverseFromSymbol`
- `inverseToSymbol`
- `cexOrderbook`
- `usedSource`
- `usedSourceReal`
- `hasUnreadAlert`
- `isSoundActive`
- `logShown`

暂停时保留的运行态内容：

- `fromSymbol`
- `toSymbol`

原因：

- 清理价格数据后，暂停交易对不会再被路径计算和报警逻辑当成可用报价
- 保留 symbol 可以继续给主看板和设置弹窗提供名称展示

### 2. 主看板 UI

文件：

- `app.js`
- 与主看板条目样式相关的静态页面样式文件

行为设计：

- `createQuoteItem()` 为每条交易对增加暂停/恢复按钮
- 按钮文案用图标表达即可，但 title 必须明确是“暂停交易对”或“恢复交易对”
- 暂停状态通过额外 class 标记整条 `quote-item`
- 结果区在暂停状态下统一显示“已暂停”
- 若 `quoteMonitorState` 中已有 symbol，则仍展示代币对名称
- 反向报价 DOM 节点在暂停时移除，避免遗留旧值

暂停按钮不使用确认框，点击即生效。

### 3. 套利路径

文件：

- `app.js`

行为设计：

- 所有进入 `window.ArbPaths.buildEdges(...)` 的 quotes 集合都改为只传入未暂停交易对
- 分类路径、全局路径、固定规则、特殊规则都使用活跃交易对视图

覆盖点：

- 全局套利路径面板
- 分类套利路径面板
- 固定规则路径
- 特殊规则路径

效果：

- 暂停交易对会立即从路径图中消失
- 相关套利机会重新计算，避免继续引用旧报价

### 4. 报警

文件：

- `app.js`
- `server.js`
- `path-alerts-app.js`

行为设计：

- 路径报警和规则报警的求值上下文只暴露活跃交易对对应的 state
- 已保存但引用暂停交易对的路径报警，在评估时会因取不到活跃 state 而进入 `unavailable`
- 规则报警在构建 edges 时只使用未暂停交易对

候选列表设计：

- `server.js` 中 `buildPathAlertQuoteCandidatesFromConfig()` 过滤暂停交易对
- `path-alerts-app.js` 中本地 fallback 的 `buildQuoteCandidates()` 也过滤暂停交易对

效果：

- 新建报警时不能再选择已暂停交易对
- 旧报警不会继续使用暂停前残留价格触发

### 5. 队列统计

文件：

- `queue-stats-utils.js`

行为设计：

- 暂停交易对不计入 `quoteCount`
- 暂停交易对不计入 `mainTasks`
- 暂停交易对不计入 `inverseTasks`
- 暂停交易对不计入 `taskCount`

效果：

- 队列统计能真实反映暂停后 task 数下降
- 用户可以直观看到暂停功能对轮询负载的影响

## 状态切换流程

### 暂停

1. 用户点击暂停按钮
2. 设置 `quote.paused = true`
3. 从所有 scheduler 队列移除该交易对任务
4. 中止该交易对正在进行中的请求（如果存在）
5. 清理价格/报警/错误相关运行态，但保留已有 symbol
6. 清理反向报价 DOM
7. 更新主看板样式与结果显示
8. 触发一次套利路径刷新与报警重评估
9. 保存配置

### 恢复

1. 用户点击恢复按钮
2. 设置 `quote.paused = false`
3. 重新加入对应 scheduler 队列
4. 更新主看板样式
5. 立即触发一次主向报价
6. 新报价成功后重新参与路径与报警
7. 保存配置

## 错误处理

- 暂停/恢复是本地配置与前端运行态操作，不依赖额外后端 API，因此不需要额外错误弹窗流程
- 如果保存配置失败，沿用现有 `saveData()`/`performSave()` 的失败提示
- 如果恢复后立即触发的首次报价失败，沿用现有报价失败展示逻辑，不影响已恢复状态
- 如果暂停时该交易对有进行中的请求，直接 `abort`，并确保 `AbortError` 不回写错误状态

## 测试策略

### 自动化测试

- `queue-stats-utils.test.js`
  - 暂停交易对不再计入队列统计
- `path-alert-candidates-api.test.js`
  - 暂停交易对不会出现在后端候选列表
- `path-alerts-app.js` 对应测试或可抽离的纯函数测试
  - 本地 fallback 候选列表过滤暂停交易对
- 前端纯逻辑测试
  - 暂停后路径计算输入不再包含该交易对
  - 暂停后报警评估上下文不再包含该交易对可用价格

### 手工验证

- 已有报价名称的交易对暂停后：
  - 保留名称
  - 价格文本变为“已暂停”
  - 行样式置灰
  - 无确认弹窗
- 暂停后：
  - 不再继续轮询
  - 反向报价消失
  - 报警高亮和错误态清除
  - 套利路径面板立即重算
- 恢复后：
  - 重新入队
  - 立即发起一次报价
  - 成功后重新参与套利路径和报警
- 队列统计页：
  - 暂停前后 task 数有明显变化

## 风险与取舍

### 已接受的取舍

- 暂停后的 symbol 只保留在当前前端运行态中，不做持久化
- 因此如果页面刷新，暂停中的交易对可能失去之前已解析的代币名展示，回退到现有兜底展示

这是刻意接受的简化，用来避免新增 metadata 读取逻辑和 symbol 持久化逻辑。

### 主要风险

- 如果仅从 UI 层置灰但没有同步过滤路径/报警/候选/统计，会产生语义不一致
- 如果暂停时不清理价格运行态，旧报价可能继续被路径或报警误用

因此实现必须覆盖以下四条链路：

1. 报价队列
2. 套利路径
3. 路径报警与规则报警
4. 候选腿与队列统计

## 实现边界结论

本次功能应通过“交易对配置新增 `paused` 字段 + 上游统一过滤活跃交易对 + 暂停时清理价格运行态”的方式实现。

这是一种最小改动方案，能够在不改底层算法模块的前提下，把“暂停=伪删除”的语义稳定地覆盖到报价、套利路径、报警、候选列表和队列统计这几条关键依赖链路。
