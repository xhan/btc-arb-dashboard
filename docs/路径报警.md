# 路径报警系统方案

## 背景与目标

新增一套独立于主看板配置的路径报警系统，核心目标是：

- 支持对一条固定套利路径持续监控收益
- 支持对一条规则模板持续监控收益
- 支持阈值报警、延迟确认、冷却周期重复提醒
- 支持从套利路径面板一键导入，也支持在独立面板手工创建
- 配置单独保存到 `alert.json`，不与 `config.json` 耦合

当前版本的范围限定为：

- 报警动作只做声音 + 日志
- Webhook 只预留配置，不实际发送
- 数据来源只使用当前 live quote 状态，不使用历史快照

## 核心设计

### 1. 独立配置文件

新增独立配置文件：`alert.json`

兼容说明：

- 服务端默认读写 `alert.json`
- 如果 `alert.json` 不存在，会回退读取旧的 `alert.config`
- 一旦保存，统一写回 `alert.json`

采用 JSON 内容，结构如下：

```json
{
  "version": 1,
  "settings": {
    "pathAlertEvalIntervalMs": 1000,
    "defaultCooldownSec": 300,
    "webhookEnabled": false,
    "webhookUrl": "",
    "webhookSecret": ""
  },
  "alerts": []
}
```

说明：

- `version`：后续配置升级用
- `settings.pathAlertEvalIntervalMs`：独立评估周期，默认 `1000ms`
- `settings.defaultCooldownSec`：默认冷却时间，默认 `300s`
- `alerts`：路径报警规则列表

### 2. 独立接口

新增服务端接口：

- `GET /api/get-alert-config`
- `POST /api/save-alert-config`

接口职责：

- 读取 `alert.json`
- 保存 `alert.json`
- 做基础默认值补齐和结构归一化

不复用现有：

- `GET /api/get-config`
- `POST /api/save-config`

这样可以减少路径报警与主看板配置的耦合。

### 3. 两类报警目标

路径报警顶层分成两类目标：

#### 3.1 `target.type = "path"`

用于固定 legs 的收益乘积公式。

适用来源：

- 手工逐腿添加
- 从普通套利路径机会导入

结构示例：

```json
{
  "id": "alert_xxx",
  "name": "WBTC 三腿套利",
  "enabled": true,
  "thresholdBp": 3,
  "triggerMode": "immediate",
  "confirmDelaySec": 0,
  "cooldownSec": 300,
  "delivery": {
    "sound": true,
    "log": true,
    "webhookEnabled": false
  },
  "target": {
    "type": "path",
    "legs": [
      {
        "quoteId": "quote_1",
        "direction": "forward",
        "pricingMode": "raw",
        "chain": "arbitrum",
        "fromSymbol": "cbBTC",
        "toSymbol": "WBTC"
      },
      {
        "quoteId": "quote_2",
        "direction": "forward",
        "pricingMode": "raw",
        "chain": "monad",
        "fromSymbol": "WBTC",
        "toSymbol": "BTC.b"
      }
    ]
  }
}
```

`PathAlertQuoteLeg` 支持字段：

- `quoteId`
- `direction: "forward" | "inverse"`
- `pricingMode: "raw" | "cex-bid1" | "cex-ask1-inverse"`
- `chain`
- `fromSymbol`
- `toSymbol`

约束：

- 手工路径只允许真实报价腿
- 不手工暴露 alias 规则腿
- 规则腿如果存在，只通过规则模板目标求值，不在手工 path 里显式配置

#### 3.2 `target.type = "rule"`

用于引用一条规则模板，而不是保存固定 legs。

适用来源：

- 从固定路径导入
- 从特殊规则导入
- 路径报警面板直接选择固定规则 / 特殊规则创建

结构示例：

```json
{
  "id": "alert_xxx",
  "name": "GHO <-> USDC",
  "enabled": true,
  "thresholdBp": 2,
  "triggerMode": "delayed",
  "confirmDelaySec": 5,
  "cooldownSec": 300,
  "delivery": {
    "sound": true,
    "log": true,
    "webhookEnabled": false
  },
  "target": {
    "type": "rule",
    "ruleKind": "fixed",
    "ruleId": "fixed:gho-usdc"
  }
}
```

说明：

- `ruleKind`：当前支持 `fixed`、`special`
- `ruleId`：引用稳定规则 ID
- 规则报警每次评估时，按当前规则模板重新求值
- 当 `ruleKind = "special"` 时，报警项额外保存：
  - `specialRuleConfig.minNetProfit`
  - `specialRuleConfig.minNetProfitBp`

特殊规则报警配置示例：

```json
{
  "id": "rule-alert-special-usde-bybit",
  "name": "USDe <-> BYBIT",
  "enabled": true,
  "thresholdBp": 0,
  "triggerMode": "delayed",
  "confirmDelaySec": 10,
  "cooldownSec": 120,
  "target": {
    "type": "rule",
    "ruleKind": "special",
    "ruleId": "special:usde-bybit"
  },
  "specialRuleConfig": {
    "minNetProfit": 8,
    "minNetProfitBp": 0
  }
}
```

这意味着：

- `GHO <-> USDC` 这类固定路径可以做成规则报警
- `DEX <-> CEX` 这类特殊规则也可以做成规则报警
- 后续新增其他特殊规则时，也能复用同一套模型

### 4. 规则模板稳定 ID

现有规则需要补稳定 ID，避免通过标题字符串匹配：

#### 固定路径规则

示例：

- `fixed:wbtc-eth-arb`
- `fixed:gho-usdc`

#### 特殊规则

示例：

- `special:wbtc-bybit`
- `special:usde-bybit`

要求：

- ID 稳定
- 不依赖 UI 标题
- 允许后续规则标题调整而不影响报警配置

## 评估引擎

### 1. 独立调度

路径报警评估器使用独立 scheduler，不依赖套利路径面板刷新。

规则：

- 使用独立 `setInterval`
- 周期来自 `alert.config.settings.pathAlertEvalIntervalMs`
- 默认 `1000ms`
- 可配置

依赖关系：

- 调度独立
- 数据仍复用当前 live quote 状态
- 如果主报价轮询暂停，路径报警自然也不会拿到新价格

这样可以避免和套利路径面板耦合过深。

### 1.1 特殊规则内置报警项

当前实现里，`special` 规则报警项按“内置项”处理：

- 加载配置时，会检查当前内置特殊规则列表
- 如果 `alert.json` 里缺少对应报警项，会自动补一条默认配置
- 默认配置包含：
  - `enabled`
  - `triggerMode`
  - `confirmDelaySec`
  - `cooldownSec`
  - `specialRuleConfig.minNetProfit`
  - `specialRuleConfig.minNetProfitBp`

这意味着：

- 特殊规则报警不适合通过“删除”来关闭
- 删除后，下次重新加载配置时会被自动补回
- 如果不想收某条特殊规则报警，应使用“禁用”

请保持这个行为，避免后续改动把“内置项自动补齐”删掉，导致特殊规则报警配置再次散落或丢失。

### 2. path 目标求值

对 `target.type = "path"`：

1. 遍历保存的 `legs`
2. 从 `quoteMarketState` 查对应 `quoteId` 的最新状态
3. 按 `pricingMode` 取值：
   - `raw`：
     - `direction=forward` => `lastRawPrice`
     - `direction=inverse` => `inverseRawPrice`
   - `cex-bid1`：`cexOrderbook.bestBidPrice`
   - `cex-ask1-inverse`：`1 / cexOrderbook.bestAskPrice`
4. 任一腿缺价，则该路径状态为 `unavailable`
5. 全部可用时，收益计算：

```text
profitRate = 所有腿价格连乘 - 1
profitBp = profitRate * 10000
```

### 3. rule 目标求值

对 `target.type = "rule"`：

- `fixed`：复用当前固定路径求值逻辑
- `special`：复用当前特殊规则求值逻辑
- 若当前规则没有可用实现，则标记为 `unavailable`

这样规则报警会自动跟随当前规则逻辑，而不是绑定导入时那一帧的临时 legs。

## 报警状态机

### 1. 运行时状态

运行时状态不持久化，只保存在前端内存：

- `status: idle | pending_confirm | cooldown | unavailable`
- `eligibleSince`
- `cooldownUntil`
- `lastTriggeredAt`
- `lastEvaluatedProfitBp`
- `lastAvailableAt`

### 2. immediate 模式

规则：

- 当前收益 `>= thresholdBp`
- 且当前时间 `>= cooldownUntil`
- 则立即报警

报警后：

- 设置 `lastTriggeredAt = now`
- 设置 `cooldownUntil = now + cooldownSec`

### 3. delayed 模式

规则：

- 首次达标时，记录 `eligibleSince = now`
- 在 `confirmDelaySec` 期间不报警
- 达到确认时间后再次评估：
  - 若仍达标 => 报警
  - 若不达标 => 回到 `idle`

### 4. 冷却与延迟是否冲突

当前设计中，两者职责分离：

- 延迟确认：判断达标是否稳定
- 冷却周期：限制报警频率

具体语义：

1. 达标但处于冷却期内
- 不报警
- 保持 `eligibleSince`
- 不重复创建新的 pending 状态

2. 冷却结束后若仍连续达标
- 可以再次报警
- 不要求必须先跌回阈值下方

3. 达标期间若收益跌破阈值
- 重置 `eligibleSince`
- 取消 `pending_confirm`

这个定义下：

- 延迟确认不会吞掉冷却
- 冷却不会制造重复 pending
- 不会出现 5 分钟内连续多次报警的隐性 bug

### 5. 当前实现约束（请保持）

这一节记录的是当前代码已经确认过的实际语义，后续若要修改，必须连同测试和本文档一起更新。

- 适用范围：
  - `path` 路径报警
  - `quote` 单腿交易对报警
  - `special` 特殊规则报警
- 三类报警的语义保持一致：
  - 首次进入命中条件时，才开始计算 `confirmDelaySec`
  - 在 `confirmDelaySec` 内如果条件消失，则本次等待作废
  - 中间条件消失后再次出现，会重新开始新的 `confirmDelaySec`
- 报警触发后进入 `cooldown`
- `cooldown` 期间如果条件一直成立：
  - 不会重复报警
  - 也不会要求必须先跌回阈值下方
- `cooldown` 结束时如果条件仍持续成立：
  - 允许直接再次报警
  - 不会重新等待一轮 `confirmDelaySec`
- 只有当条件中途消失，再次恢复时，才会重新等待 `confirmDelaySec`

换句话说：

- `confirmDelaySec` 负责过滤“刚出现的短抖动”
- `cooldownSec` 负责限制“已经确认过的机会”的重复提醒频率

## UI 设计

### 1. 独立“路径报警”面板

新增独立面板，职责包括：

- `+ 添加路径报警`
- 展示已配置报警列表
- 显示运行状态
- 提供启用、编辑、删除操作

每条规则展示：

- 名称
- 类型：`路径` / `固定规则` / `特殊规则`
- 路径摘要
- 当前收益 `bp`
- 阈值 / 延迟 / 冷却
- 当前状态：
  - `监控中`
  - `待确认`
  - `冷却中`
  - `缺报价`
  - `已禁用`
- 上次报警时间
- 操作按钮：启用、编辑、删除

### 2. 手工添加路径

“添加路径报警”弹窗分 3 个来源：

- `手工路径`
- `固定规则`
- `特殊规则`

#### 手工路径

交互风格参考图表页的“添加图表”，但候选源改为当前 live quotes。

支持：

- 搜索候选报价对
- 逐腿添加
- 删除腿
- 调整顺序
- 保存前预览当前收益

不支持：

- 直接从历史快照候选中选
- 手工添加 alias 规则腿

#### 固定规则 / 特殊规则

直接展示当前可用规则模板列表：

- 固定路径：如 `GHO <-> USDC`
- 特殊规则：如 `DEX <-> CEX`

选择后直接创建 `target.type = "rule"` 的报警规则。

### 3. 从套利路径一键导入

在套利路径机会卡片上增加 `+` 按钮。

导入逻辑：

- 普通套利机会 => 创建 `target.type = "path"`
- 固定路径 => 创建 `target.type = "rule"`
- 特殊规则 => 创建 `target.type = "rule"`

默认参数：

- `thresholdBp`：空
- `triggerMode = "immediate"`
- `confirmDelaySec = 0`
- `cooldownSec = 300`
- `delivery.sound = true`
- `delivery.log = true`
- `delivery.webhookEnabled = false`

路径报警配置使用独立自动保存，不依赖主看板保存按钮。

触发时机：

- 创建
- 编辑
- 启用/禁用
- 删除
- 修改全局设置（如评估周期）

原因：

- 路径报警配置已经脱离主看板配置
- 用户预期是独立功能独立保存
- 避免和 `config.json` 的保存节奏互相影响

- 规则报警依赖规则模板有稳定 ID
- live quote 状态是唯一本期数据源
- 快照回放不纳入本期路径报警能力

## 实现结论

本方案的核心原则是：

- 配置独立
- 调度独立
- 报警模型分为 `path` 与 `rule`
- 延迟确认和冷却周期解耦
- 固定路径与特殊规则统一纳入规则报警模型
- 普通套利机会导入为固定 legs 路径报警

## 当前实现补充（2026-03-13）

这一节描述的是**当前已经落地的真实行为**，优先级高于上面的早期设计描述。

### 1. 当前配置与默认值

当前 `alert.config.settings` 里实际使用的关键字段：

- `pathAlertEvalIntervalMs = 1000`
- `defaultCooldownSec = 180`
- `changedLegMinBp = 0.1`
- `localSoundEnabled = true`
- `webhookEnabled = true`
- `dayAppEnabled = false`
- `telegramEnabled = true`

说明：

- 路径报警现在每 `1000ms` 评估一轮
- 冷却默认 `180s`
- 异动腿只显示绝对值 **大于 `0.1bp`** 的腿
- 远程推送当前默认只走 **Telegram**
- `day.app` 通道已保留配置能力，但默认关闭

### 2. 当前报警目标语义

当前仍保留两类报警：

- `target.type = "path"`
- `target.type = "rule"`

其中：

- `path`：盯固定的一组 legs
- `rule`：盯一条规则模板当前的最优结果

当前 fixed/special 规则已经改成**共享计算结果**：

- 套利路径 UI 和 `rule` 报警共用同一份规则结果快照
- 不再出现“UI 算一次、报警再算一次”的重复计算

### 3. 当前 fixed / special 规则行为

fixed path 已经支持：

- `chains`
- `crossChain`
- `categoryNames`
- `excludeChains`
- `excludeSymbols`
- `resultLimit`

说明：

- `chains`：写死链范围
- `crossChain`：动态枚举不同链
- `categoryNames`：限定搜索分区
- `excludeChains`：排除某些链
- `excludeSymbols`：排除某些代币
- `resultLimit`：这条 fixed rule 在 UI 最多展示多少条结果

同时：

- `findFixedPaths(...)` 返回排序后的结果列表
- `findBestFixedPath(...)` 只是兼容层，内部取第一条

### 4. 当前触发逻辑

#### immediate

- 当前收益达到阈值
- 且不在冷却期
- 立即报警

#### delayed

- 当前收益第一次达到阈值
- 进入“观察”
- 等待 `confirmDelaySec`
- 等待结束时如果仍然达到阈值，则报警

这里的关键语义是：

- `delayed` 只负责判断“这条机会是否稳定成立”
- 不负责解释“哪条腿动了”

### 5. 当前异动腿逻辑

异动腿现在单独按一套更直接的规则处理：

- 报警命中后，只分析**当前命中路径**里的真实腿
- 每条腿按：
  - `quoteId`
  - `direction`
  - `pricingMode`
  匹配基线
- 只输出变化绝对值 **大于 `changedLegMinBp`** 的腿
- 默认最多展示前 `3` 条

#### 基线怎么取

`immediate`：

- 基线 = **上一轮评估时的全市场腿快照**

`delayed`：

- 基线 = **进入观察前一轮的全市场腿快照**

这条规则的目的很明确：

- 报警负责判断“等了 13 秒后是否还成立”
- 异动腿负责解释“相对刚过线前，哪条腿把它推上去了”

#### 快照的存储方式

- 快照只存在前端内存里
- 不落盘
- 不做长期历史累积
- 每轮覆盖更新

因此当前不会因为运行时间长而无限堆积快照。

### 6. rule 报警在观察期内路径切换时的语义

对于 `rule` 报警：

- 观察期开始时，不锁死当时那条具体路径
- 观察结束时，取这条规则**当前最新的最优路径**做最终判断

也就是说：

- 如果规则的最佳路径在等待期间换了
- 只要等待结束时这条规则仍然大于阈值
- 就会报警

异动腿的处理方式是：

- 仍然只看**最终命中路径**里的腿
- 再去和“进入观察前一轮”的全市场快照比较

所以当前 `rule` 报警的语义是：

- 盯的是“规则模板当前最优结果”
- 不是“观察开始时那条具体路径”

### 7. 当前通知格式

现在报警通知已经区分单条和多条：

#### 单条

`title`：

- 直接用这条报警的标题

`body`：

- 第一行：收益
- 后面：当前命中路径的腿
- 如果有异动腿，再追加：
  - `异动腿:`
  - 每条腿单独一行

#### 多条

`title`：

- `N 条`

`body`：

- 每条报警作为一个 block
- 每个 block 内部结构同单条

### 8. 当前远程推送逻辑

当前远程推送已经不是“只预留不发送”，而是已经落地：

- 路径报警命中后会走 `/api/send-path-alert-webhook`
- 服务端按配置决定发哪些通道

当前支持：

- Telegram Bot API
- `day.app`

当前默认值：

- `Telegram = 开`
- `day.app = 关`

因此当前线上实际效果是：

- 远程推送默认只发 Telegram

### 9. 当前批量导入与“不需要路径”

当前已支持：

- 主看板路径报警窗口里 `导入当前全部机会`
- `删除`
- `标记并删除`

并维护：

- `dismissedTargets`

语义：

- `删除`：只删报警
- `标记并删除`：删报警，并加入“不需要路径列表”
- 以后再次批量导入时，命中 `dismissedTargets` 的路径会自动跳过

### 10. 当前 identity 规则

对于 `path` 报警：

- 同一闭环，不同起点，算同一个
- 真正反方向，算不同

这套规则统一用于：

- 去重
- 批量导入跳过
- `dismissedTargets` 命中判断
